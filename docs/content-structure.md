# 연수위키 — 콘텐츠 구조 설계

나무위키 인물 문서의 각 컴포넌트를 포트폴리오 콘텐츠로 치환한 매핑. 원본 분석: `namuwiki-ux-analysis.md`

**설계 원칙**: 형식은 나무위키 그대로 두고 **내용만 갈아끼운다.** 형식을 건드리는 순간 패러디가 아니라 "위키 느낌 나는 사이트"가 됨.
동시에 모든 패러디 요소는 **실제 채용/협업 관점에서도 기능**해야 함 (아래 "실제 기능" 열 참고).

## ✅ 확정 사항 (2026.08.14)

1. **문서 구조: 메인 + 하위 3개** — 경력 / 프로젝트 / 기술 스택을 별도 문서로 분리.
   → TOC 파랑·검정 혼재 규칙이 살아나고, 프로젝트 상세를 개별 문서로 확장 가능.
2. **톤: 본문 진지 + 각주 개그** — 본문은 건조한 3인칭 위키 서술체로 실제 커리어 정보를 전달하고,
   유머는 각주·핫노트·라이선스 고지에만 배치 (아래 F항 원칙).

## B. 문서 트리 (파란 링크 = 별도 하위 문서)

```
공연수                                  ← 메인 문서
├─ 공연수/경력          [파랑]
├─ 공연수/프로젝트      [파랑]
│   ├─ 공연수/프로젝트/숏폼 PLC 분석
│   └─ 공연수/프로젝트/스마트물류 리콜 모니터링
├─ 공연수/기술 스택     [파랑]
└─ 공연수/여담          [검정, 문서 내 앵커]
```

> TOC 색상 규칙(파랑=하위 문서 보유 / 검정=내부 앵커)을 살리려면 **최소 2~3개는 실제로 분리**해야 함. 전부 내부 앵커면 색이 전부 검정이라 이 시그니처가 죽음.

**확정된 라우팅**

| 경로 | 문서 | TOC 색 |
|---|---|---|
| `/w/공연수` | 메인 | — |
| `/w/공연수/경력` | 3. 경력 | 파랑 |
| `/w/공연수/프로젝트` | 4. 프로젝트 | 파랑 |
| `/w/공연수/기술 스택` | 5. 기술 스택 | 파랑 |
| `#s-1`, `#s-2`, `#s-6` … | 개요 / 작업 스타일 / 여담 · 어록 | 검정 |

하위 문서에도 **동일한 헤더 + 인포박스(축약형) + 상단 "상위 문서: 공연수" 링크**를 반복 배치할 것.
나무위키 하위 문서의 그 반복성이 "진짜 위키 같다"는 인상의 큰 부분임.

## C. 메인 문서 섹션 구성

원본(프로게이머 문서)의 섹션 순서를 최대한 보존하면서 치환.

| # | 원본 | 연수위키 | 내용 |
|---|---|---|---|
| 1 | 개요 | **개요** | 3~4문장. "대한민국의 OOO. 현재 OO 소속." 한 문단으로 정체성 확정 |
| 2 | **플레이 스타일** ★ | **작업 스타일** ★ | 이 문서의 핵심. 아래 D 참고 |
| 3 | 선수 경력 [파랑] | **경력** [파랑] | 연도별. 하위 문서로 분리 |
| 4 | 수상 경력 | **수상 · 성과** | 대회/공모전/장학금, 표 형태 |
| 5 | 밈 [파랑] | **여담** | 개그 밀도 최고 구간 |
| 6 | 어록 | **어록** | 인용문 블록. 작업 철학을 대사로 |
| 7 | 논란 | *(선택)* **한계 / 보완 중인 점** | 아래 참고 |
| 8 | 관련 문서 | **관련 문서** | 프로젝트·링크 목록 |

### 섹션 2 "작업 스타일"이 왜 핵심인가

프로게이머 문서의 "플레이 스타일"은 **강점 → 약점 → 총평** 순의 서술형 평가 문단이다.
포트폴리오에서 자기 강점을 쓰면 보통 자화자찬이 되는데, **위키의 3인칭 평가체를 빌리면 자연스럽게 읽힌다.** 형식이 내용을 정당화하는 구조.

```
2. 작업 스타일

  데이터 분석과 기획 문서 작성을 동시에 소화하는 것이 최대 강점이다.[7]
  특히 정량 분석 결과를 의사결정자가 읽을 수 있는 형태로 번역하는 데 ...

2.1. 강점
2.2. 약점        ← 여기까지 쓰면 진정성이 급상승함
```

> 원본의 "논란" 섹션을 **"약점"으로 흡수**하는 걸 추천. 별도 "논란" 섹션은 패러디로는 웃기지만
> 채용 담당자가 스캔할 때 위험 신호로 오독될 여지가 있음. 2.2에 녹이면 "자기 객관화 되는 사람"으로 읽힘.

## E. 핫노트 & 라이선스 (개그 배치 지점)

문서 상단·하단의 **정형 문구**를 비트는 게 패러디 밀도를 가장 싸게 올리는 방법.

```
[상단 핫노트]
➜ 이 문서는 실존 인물을 다룹니다. 사실과 다른 내용이 있다면 편집 요청 바랍니다.
➜ 동명이인에 대한 내용은 (해당 문서) 문서를 참고하십시오.

[하단 라이선스]
이 문서의 내용 중 전체 또는 일부는 공연수 본인이 작성하였으며,
사실 여부는 본인만이 검증할 수 있습니다.
```

## F. 각주 활용 원칙

각주는 **본문 톤을 진지하게 유지하면서 개그를 분리 수납**하는 장치.
본문은 건조한 위키체로 쓰고, 웃긴 건 전부 각주로 내리면 두 톤이 동시에 성립한다.

```
본문:  ... 팀 내 문서화를 전담했다.[12]
각주:  [12] 아무도 하겠다고 하지 않았기 때문이다.
```

원본에 없던 **복귀 링크(↩)는 추가**하기로 결정 (없어도 패러디는 성립하지만 이탈이 실제로 발생함).
